## Task Package

**Task ID**: `TASK-NANE-AUTH-001`  
**Title**: 增加邮箱账号密码登录与密码找回  
**Priority**: P1  
**Estimated Scope**: 大（> 200 行）

---

### Context

当前网页端首选南京大学学生邮箱验证码登录，邮箱后缀固定为 `@smail.nju.edu.cn`。测试反馈希望注册/首次登录时可设置密码，后续用密码登录，并支持忘记密码找回。

相关文件：

- `server/index.js` — 邮箱验证码、用户登录、JWT 签发逻辑
- `server/db.js` — 启动时数据库迁移
- `server/schema.sql` — PostgreSQL schema
- `web/index.html` — 登录区 DOM
- `web/app.js` — 邮箱登录前端逻辑
- `web/styles.css` — 登录区样式
- `.env.example` — 邮件配置说明
- `docs/test-guide.md` — 验收流程
- `docs/development-log.md` — 开发日志

---

### Requirements

1. 为 `users` 增加可空 `password_hash` 字段，兼容已有用户。
2. 使用服务器端安全哈希保存密码；不得明文保存密码。可以复用现有 `hashPassword()`，但需评估是否应加入用户维度 salt；若保持现状，需在完成报告说明原因。
3. 邮箱验证码登录成功后，如果用户尚未设置密码，前端提示用户设置密码；设置后保存到后端。
4. 增加邮箱 + 密码登录接口，仅允许 `@smail.nju.edu.cn` 后缀账号。
5. 增加“忘记密码”流程：发送邮箱验证码，验证通过后允许重设密码。
6. 前端登录区保留现有邮箱验证码登录，同时新增“密码登录”和“忘记密码”入口。
7. 密码规则：至少 8 位，最多 64 位；至少包含字母和数字；前后端都校验。
8. 成功密码登录后仍签发现有 NanE JWT，并保留用户协议与账号资料完整性检查。
9. 更新测试文档与开发日志。

---

### Constraints

- 不要删除现有邮箱验证码登录；验证码仍是首选注册/找回方式。
- 不要改变游客浏览公开物品的能力。
- 不要允许非 `@smail.nju.edu.cn` 邮箱注册或登录。
- 不要把 SMTP 授权码、JWT_SECRET 或任何密钥写入前端或 Git。
- 不要引入大型前端框架。

---

### Acceptance Criteria

- [ ] AC-1：已有邮箱验证码登录仍可用。
- [ ] AC-2：首次邮箱验证码登录后，可设置密码。
- [ ] AC-3：设置密码后，可使用邮箱前缀 + 固定后缀 + 密码登录。
- [ ] AC-4：错误密码返回明确错误，不泄露账号是否存在的敏感细节。
- [ ] AC-5：忘记密码流程可发送验证码并重设密码。
- [ ] AC-6：非 `@smail.nju.edu.cn` 邮箱被前后端拒绝。
- [ ] AC-7：`users.password_hash` 可通过启动迁移自动添加，旧数据不崩。
- [ ] AC-8：`node --check server/index.js` 和 `node --check web/app.js` 通过。

---

### Test Expectations

```bash
node --check server/index.js
node --check web/app.js
```

手动回归：

1. 邮箱验证码登录。
2. 首次登录后设置密码。
3. 退出后密码登录。
4. 忘记密码重设。
5. 游客浏览、发布、查看联系方式不回归。

## Task Package

**Task ID**: `TASK-NANE-CLAIM-002`  
**Title**: 优化领取确认提醒的邮件跳转与站内入口位置  
**Priority**: P0  
**Estimated Scope**: 中（50-200 行）

---

### Context

当前领取者点击“我已联系并领取，提醒发布者确认”后，系统会发送邮件，并在发布者“我的发布”物品卡中显示待确认领取提醒。测试反馈认为邮件应有直接跳转按钮，且确认模块位置偏下，发布者可能找不到。

相关文件：

- `server/index.js` — `sendMail()`、`sendClaimNotificationMail()`、领取提醒接口
- `web/index.html` — 我的页结构
- `web/app.js` — 我的发布渲染、领取确认按钮、视图切换逻辑
- `web/styles.css` — 领取提醒样式
- `docs/test-guide.md` — 领取确认验收流程
- `docs/development-log.md` — 开发日志

---

### Requirements

1. 领取确认邮件改为支持 HTML 邮件，同时保留纯文本 fallback。
2. 邮件中增加醒目的按钮文案：`去 NanE 确认领取`。
3. 按钮链接到 `PUBLIC_WEB_URL`，并携带可被前端识别的参数，例如 `?view=mine&focus=claims`。
4. 前端初始化时识别 `view=mine`，自动切到“我的”页。
5. 前端识别 `focus=claims` 时，在我的页优先定位到待确认领取区域。
6. 我的页顶部新增“待确认领取提醒”区域，仅当存在待确认领取请求时展示；该区域应出现在“我的发布”列表上方。
7. 我的发布列表中有待确认请求的物品仍保留卡片内确认/忽略按钮，但待确认物品应优先排序在列表前方。
8. 确认或忽略后，顶部提醒区和列表同步刷新。
9. 更新测试文档与开发日志。

---

### Constraints

- 不要破坏当前站内领取确认流程。
- SMTP 发送失败时，站内提醒仍必须创建成功。
- 不要在邮件里暴露发布者宿舍号、微信、QQ。
- 不要改变每日联系方式查看限额逻辑。

---

### Acceptance Criteria

- [ ] AC-1：领取者发起提醒后，发布者收到 HTML 邮件，邮件内有可点击按钮。
- [ ] AC-2：点击邮件按钮后打开网站并自动进入“我的”页。
- [ ] AC-3：如果存在待确认领取，页面顶部展示待确认提醒。
- [ ] AC-4：发布者可在顶部提醒区确认或忽略。
- [ ] AC-5：确认后数量扣减；数量归零时物品状态变为 `claimed` 并从首页消失。
- [ ] AC-6：忽略后该提醒不再显示。
- [ ] AC-7：`node --check server/index.js` 和 `node --check web/app.js` 通过。

---

### Test Expectations

```bash
node --check server/index.js
node --check web/app.js
```

手动回归：

1. A 发布物品，管理员审核通过。
2. B 查看联系方式并发起领取提醒。
3. A 收到邮件，点击按钮进入“我的”页。
4. A 在顶部提醒区确认领取。
5. 首页确认物品下架或数量更新。

## Task Package

**Task ID**: `TASK-NANE-FILTER-003`  
**Title**: 首页增加药品分类筛选标签并修正文案  
**Priority**: P0  
**Estimated Scope**: 中（50-200 行）

---

### Context

测试截图显示物品卡片上已有 `过敏药` 标签，但首页搜索栏下方只有 `全部 / 应急耗材 / 非处方药品`，用户无法直接按 `过敏药` 筛选。另有测试意见要求修改发布声明文案。

相关文件：

- `web/index.html` — 首页筛选 chips、发布声明文案
- `web/app.js` — `filterChips`、`loadHome()` 查询参数
- `web/styles.css` — chips 样式
- `server/index.js` — `/api/items` 已支持 `category` 查询参数
- `docs/test-guide.md` — 首页筛选与发布声明验收
- `docs/development-log.md` — 开发日志

---

### Requirements

1. 首页搜索栏下方新增药品分类筛选 chips：`感冒药`、`退烧药`、`过敏药`、`肠胃药`、`其他非处方药`。
2. 点击药品分类 chip 时，请求 `/api/items?itemType=medicine&category=<分类>`。
3. 点击 `非处方药品` 时，仅筛选 `itemType=medicine`，不固定 category。
4. 点击 `应急耗材` 时，仅筛选 `itemType=consumable`，并清空 category。
5. 点击 `全部` 时清空 itemType 与 category。
6. 当前选中的 chip 应有清晰 active 状态；切换筛选时列表立即刷新。
7. 搜索关键词与分类筛选应能叠加使用。
8. 将发布声明中的 `拆封不明物品` 改为测试意见要求的 `已拆分不明物品`。
9. 如果同一句文案在其他网页端位置重复出现，也同步修改；小程序端不在本任务范围内，除非完全同一句文案存在且明显需要保持一致。
10. 更新测试文档与开发日志。

---

### Constraints

- 不要修改后端药品分类白名单。
- 不要新增独立分类页。
- 不要改变现有搜索接口路径。
- 不要把筛选 chip 做成多选；本轮只需要单选筛选。

---

### Acceptance Criteria

- [ ] AC-1：首页出现 `过敏药` chip。
- [ ] AC-2：点击 `过敏药` 后，只展示 `itemType=medicine` 且 `category=过敏药` 的上架物品。
- [ ] AC-3：关键词搜索与 `过敏药` 筛选可叠加。
- [ ] AC-4：点击 `全部` 后恢复全量上架物品。
- [ ] AC-5：发布声明文案已按测试意见修改。
- [ ] AC-6：`node --check web/app.js` 通过。

---

### Test Expectations

```bash

```

手动回归：

1. 发布并审核一个 `药品 / 过敏药` 物品。
2. 首页点击 `过敏药`，确认该物品出现。
3. 点击 `感冒药`，确认过敏药物品不出现。
4. 点击 `全部`，确认列表恢复。
