# NanE (南易) 开发路线图

> 最后更新：2026-06-11

## 当前状态

NanE 已完成基础功能验证——用户可通过 NJU 邮箱或南哪小帮手登录、发布物品、浏览搜索、查看联系方式、发起认领。管理后台具备初步的登录和审核能力。

**已知技术债**（本路线图要解决的核心问题）：

| 维度 | 现状 | 目标 |
|------|------|------|
| 后端结构 | `server/index.js` 单文件 2150 行 | 按职责拆分为独立路由模块 |
| 前端结构 | `web/app.js` 2193 行，`styles.css` 2498 行 | 按视图/组件/API 分拆 |
| 静态资源 | Font Awesome 全量引入 (~1.6MB) | Tree-shaking 降至 KB 级 |
| 可观测性 | `console.error` 裸打日志 | 结构化日志 + 审计追溯 |
| 管理后台 | 单管理员、仅审批/下架 | 多管理员分级、用户管理、数据统计 |
| 测试 | 零测试 | 核心路径单元测试 + API 集成测试 |
| 安全 | CORS 全开、无请求体限制 | 白名单、安全头、速率限制完善 |
| 文档 | 无 API 文档 | 随模块拆分产出 API 参考 |

## 阶段一：后端架构解耦 + 观测性基础

**目标**：将单一巨石文件拆分为可独立理解和维护的模块，同时建立日志和 API 文档基础。

### 1.1 server/ 模块化拆分

将 `server/index.js` 的 `handle()` 函数按路由前缀拆分为独立模块：

```
server/
├── index.js          # HTTP 创建、静态文件、路由分发 (~150行)
├── router/
│   ├── auth.js       # /api/auth/* — 邮箱登录、南哪登录、JWT签发
│   ├── items.js      # /api/items/* — 物品CRUD、搜索、联系方式查看
│   ├── claims.js     # /api/claims/* — 认领请求与确认
│   ├── me.js         # /api/me/* — 个人信息、我的物品、设置
│   ├── admin.js      # /api/admin/* — 管理员登录、审核、统计
│   └── legal.js      # /api/legal/* — 用户协议、隐私指引
├── middleware/
│   ├── auth.js       # requireVerifiedUser()、requireAdmin()
│   └── rate-limit.js # 现有限流逻辑独立
├── service/
│   ├── email.js      # SMTP 发送（验证码、通知）
│   └── nanna.js      # 南哪小帮手 API 代理
├── db.js             # 连接池、query()、makeId()、hashPassword()
├── proximity.js      # 现有 proximity 逻辑
├── migration.js      # 独立的迁移执行器（见 1.3）
├── logger.js         # 结构化日志（见 1.2）
└── schema.sql        # 基础 DDL（不变）
```

每个路由模块导出 `function register(router)` 或一组处理函数，`index.js` 仅负责创建 HTTP server、匹配路径和分发调用。

### 1.2 结构化日志系统

新建 `server/logger.js`，提供统一的日志接口：

- **请求日志**：method + path + status + elapsed_ms + user_id（如有）
- **操作审计日志**：admin 审核/封禁/次数调整等操作，记录 who、what、target、when
- **错误日志**：至少包含 stack trace、请求上下文、时间戳
- **输出目标**：控制台（开发）+ 文件滚动写入（生产），文件按天轮转

不引入外部日志库——使用 Node 内置 `fs.createWriteStream` 追加写入，大致 100 行即可。

### 1.3 数据库迁移规范化

现状：`db.js` 的 `initializeDatabase()` 执行 `schema.sql` 后逐个 ALTER TABLE。问题在于不知道哪个 ALTER 已执行过、变更历史不可追溯。

方案：
- 创建 `server/migrations/` 目录，编号文件如 `001_add_owner_hidden.sql`
- `server/migration.js` 维护 `_migrations` 表，记录已执行的迁移
- 启动时按顺序执行尚未应用的迁移文件
- 将现有 ALTER TABLE 语句逐条抽出，写入对应迁移文件
- 此后新增字段一律走迁移文件

### 1.4 API 文档产出

随模块拆分，在 `docs/api/index.md` 生成精简 API 参考：

- 每个端点：method + path + 请求参数 + 成功/错误响应示例
- 不引入 Swagger 等框架——直接手写 Markdown 表格（约 25 个端点）

**预估时间**：1.5–2 周
**风险**：拆分过程中的回归——需要至少手动跑通核心流程（注册→登录→发布→搜索→查看联系方式→认领→审核）

## 阶段二：前端工程化重构

**目标**：将前端代码从 3 个巨大文件拆分为可维护的模块结构，同时大幅降低静态资源体积。

### 2.1 JS 模块拆分

将 `web/app.js` (~2200行) 按职责拆分：

```
web/
├── app.js              # 入口：标签切换、初始化、全局状态 (~150行)
├── api/
│   └── client.js       # fetch 封装、token 管理、401 处理
├── views/
│   ├── home.js         # 发现页：搜索、筛选、列表、分页
│   ├── publish.js      # 发布表单：校验、字数统计、提交
│   ├── mine.js         # 我的：物品管理、删除、编辑
│   └── settings.js     # 设置：登录、资料、密码、关于
├── ui/
│   ├── toast.js        # Toast 通知组件
│   ├── dialog.js       # 弹窗组件（详情、确认、登录）
│   ├── skeleton.js     # 骨架屏
│   └── dropdown.js     # 下拉菜单/选择器
└── utils/
    ├── date.js         # 日期格式化、倒计时
    ├── validate.js     # 表单校验
    └── escape.js       # XSS 防护
```

使用 ES modules（`type="module"`），现代浏览器已全覆盖，无需打包即可工作。

### 2.2 CSS 按功能分区

将 `web/styles.css` (~2500行) 拆分为：

```
web/css/
├── tokens.css          # CSS 变量：颜色、间距、圆角、阴影
├── base.css            # 重置、排版、按钮、表单等基础元素
├── layout.css          # 页面布局、卡片网格、tab 切换
├── home.css            # 发现页特定样式
├── publish.css         # 发布表单特定样式
├── mine.css            # 我的页特定样式
├── settings.css        # 设置页特定样式
├── dialog.css          # 弹窗、遮罩
├── toast.css           # Toast/通知
├── skeleton.css        # 骨架屏动画
└── responsive.css      # 媒体查询统一收口
```

通过多个 `<link>` 标签加载。阶段一不引入 CSS 打包——拆分本身就是最大的可维护性收益。

### 2.3 Font Awesome Tree-shaking

当前通过 `<link>` 全量引入 Font Awesome Free 6.x CSS（包含 2000+ 图标），实际使用不足 50 个。

方案：
- 按需创建字体子集：列出项目使用的图标清单
- 使用 `@fortawesome/fontawesome-free` npm 包 + 简单构建脚本提取 `used-icons.css`
- 或直接使用 SVG sprites 替代字体文件，进一步减小体积
- 目标：图标体积从 ~1.6MB 降至 <100KB

### 2.4 静态资源优化

- **CSS/JS 压缩**：引入简单的 npm script（如 `cleancss` + `uglify-js`），产出 `.min.css` / `.min.js`
- **文件名 hash**：构建时在文件名中加入内容 hash（如 `app.a3f8.js`），实现永久缓存
- **Cache-Control**：`index.html` 设 `no-cache`，带 hash 的静态资源设 `max-age=31536000`
- **构建脚本**：`npm run build:web` 执行压缩+hash，产物输出到 `web/dist/`，server 优先 serve dist

### 2.5 PWA 基础（可选）

- 添加 `manifest.json`（图标、名称、主题色）
- 简单 Service Worker：离线时显示缓存的骨架页 + "请联网使用"提示
- 无需完整的离线优先策略——平台的核心场景需要联网

**预估时间**：2–3 周
**风险**：拆分后功能回归——重点验证移动端窄屏、弹窗交互、表单提交流程

## 阶段三：管理后台能力升级

**目标**：将管理后台从"单管理员的审核面板"升级为"多角色运营工具"。

### 3.1 审核流程完善

当前后台审核仅二选一：通过（上线）/ 下架，驳回无理由，用户无感知。

升级内容：

- **驳回理由**：弹窗输入必填驳回原因（如"药品信息不完整""禁止品类"），记录到 `review_logs` 表
- **审核通知**：物品审核结果通过邮件通知发布者——通过告知"已上架"，驳回告知原因+修改建议
- **审核日志**：`review_logs` 扩展为完整审计记录——审核人、时间、操作、原因、物品快照
- **批量操作**：多选物品后批量通过/驳回（每日审核量增加后必需）
- **审核队列**：按提交时间排序，高亮"已等超过 24h"的积压条目

### 3.2 用户管理

新增 `GET /api/admin/users` 和 `POST /api/admin/users/:id/:action`：

- **用户列表**：搜索（ID/昵称/邮箱）、筛选（是否验证、是否被封禁）、排序
- **用户详情**：基本信息 + 发布历史 + 认领历史 + 联系方式查看次数
- **次数调整**：手动增减某用户当日/当周联系方式查看限额
- **封禁/解封**：冻结用户（禁止登录和操作）+ 封禁原因记录
- **联系用户**：通过预留邮箱或微信发送通知（个别通知或群发）

新增 `users` 表字段：`is_banned BOOLEAN DEFAULT FALSE`、`ban_reason TEXT`、`banned_at TIMESTAMPTZ`。

### 3.3 多管理员与权限分级

现状：通过 `ADMIN_PASSWORD` 环境变量单密码登录，无用户区分。

升级为：

- **管理员账户表**（`admins` 表已有，扩展）：
  - `role` 字段：`super_admin`（全部权限）/ `moderator`（仅审核）/ `viewer`（仅查看统计）
  - 管理员之间互相不可删除、不可降级自身
- **登录**：用户名+密码 + JWT，区分过期时间（admin token 8h）
- **操作追溯**：所有 admin 操作关联到具体管理员 ID，可查询某管理员的操作历史
- **初始管理员**：首次启动时创建默认超级管理员，密码来自环境变量或随机生成并打印

### 3.4 管理员 UI 独立化

当前管理后台 HTML/CSS/JS 全部内联在 `adminPage()` 函数中（~100 行 HTML + ~100 行 JS）。

方案：
- 将管理后台拆为独立目录 `admin/`，包含 `index.html`、`app.js`、`styles.css`
- Server 通过 `serveStatic` 按 `/admin/*` 路径提供服务
- 管理后台独立登录页 → 仪表盘 → 各管理模块
- 不再与主 `server/index.js` 耦合

**预估时间**：2–3 周
**依赖**：阶段一的路由拆分完成后才能顺畅添加新的 admin API

## 阶段四：数据统计与运维监控

**目标**：让运营者看到平台运行状况，数据驱动决策。

### 4.1 数据仪表盘

在管理后台首页扩展统计面板（当前仅 4 个计数器）：

- **概览卡片**（当前已有，增强）：
  - 今日新增用户 / 本周新增 / 累计
  - 今日发布 / 待审核 / 上架中 / 已认领
  - 今日联系方式查看次数 / 认领确认率
- **趋势图表**：
  - 每日新增物品折线图（7d / 30d）
  - 用户活跃趋势（DAU，以登录/操作为准）
  - 物品品类分布饼图
- 图表使用轻量方案：内联 SVG 手绘或用 `<canvas>` 手写简单折线/柱状图（不引入 Chart.js 体积太大）

### 4.2 API 性能监控

在 `server/logger.js` 基础上增加性能采集：

- **响应时间统计**：每个请求记录 elapsed_ms
- **慢查询标记**：超过 500ms 的请求单独记录
- **定时报告**：每小时汇总——请求总数、P50/P95/P99 延迟、错误率
- **暴露端点**：`GET /api/admin/health` 返回即时状态（DB 连接池、最近请求延迟分位值、内存使用）
- 不引入外部 APM 或 Prometheus——当前规模不需要

### 4.3 数据导出

- **物品列表导出**：按状态筛选后导出 CSV（ID、名称、类别、发布者、发布时间、状态）
- **用户列表导出**：CSV 格式
- **审核日志导出**：按时间范围导出审核操作记录
- 格式：CSV UTF-8 BOM（Excel 可直接打开）

### 4.4 数据库运维

- 连接池健康检查 + 泄露检测
- 定时清理过期 email_challenges（> 24h）
- 统计表行数/磁盘占用查询（管理后台可见）

**预估时间**：1.5–2 周
**依赖**：阶段三的管理后台基础

## 阶段五：质量体系与社区功能

**目标**：补全测试覆盖、安全加固、建立信任信号，让平台从"能用"到"稳定可靠"。

### 5.1 测试体系

从零开始，不追求覆盖率数字，聚焦"不可失败"的路径：

**后端单元测试**（`server/*.test.js`）：
- `db.js`：`makeId()` 格式、`hashPassword()` / `verifyPassword()` 加盐验证
- `proximity.js`：各校区楼栋映射、`sortByProximity()` 排序逻辑
- auth 中间件：`signToken()` / `verifyToken()` 正常+过期+篡改
- 使用 Node 内置 `node:test` + `node:assert`（Node 18+ 内置，无需额外安装）

**API 集成测试**（`tests/api.test.js`）：
- 注册→登录→发布物品→搜索→查看联系方式→认领→确认
- 管理员登录→审核通过→审核驳回→下架
- 未登录访问受保护端点返回 401
- 使用 `node:test` + 启动临时 server + fetch
- 测试前创建独立 PostgreSQL schema 或使用事务回滚

**前端测试**：暂不引入——纯 vanilla DOM 操作的测试成本/收益比不合理。在拆分后的模块中，对纯逻辑函数（`validate.js`、`date.js`）补充单元测试即可。

### 5.2 安全加固

- **CORS 白名单**：生产环境只允许管理后台域名 + 小程序域名，开发环境保留 `*`
- **安全头**：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Strict-Transport-Security`
- **请求体大小限制**：`server.maxHeaderSize` + 解析时检查 Content-Length，防止内存溢出
- **密码强度**：设置/修改密码时要求 ≥ 8 位 + 至少包含字母和数字
- **Rate limit 细化**：当前已有全局基础限流，增加：
  - 登录失败限流（IP + 邮箱维度）
  - 验证码发送间隔 ≥ 60s
  - 管理后台登录失败 ≥ 5 次锁定 15 分钟

### 5.3 社区信任信号

- **感谢按钮**：物品被认领后，发布者/认领者可互相发送感谢，公开显示在物品详情
- **用户档案统计**：用户主页展示"已送出 N 件"和"已领取 M 件"（不计敏感数据）
- **好评标志**：送出/领取 ≥ 10 件的用户显示徽章（如"活跃分享者"）
- 这些功能数值很小，但不引入评分或评价系统——保持平台轻量互助调性，避免竞争性

### 5.4 用户反馈闭环

- **反馈入口**：设置页"意见反馈"按钮，打开简短表单（分类 + 文字 + 可选的邮箱）
- **反馈表**：新建 `feedback` 表（id、user_id、category、content、status、created_at）
- **后台处理**：管理后台"反馈管理"页面，标记已处理/回复
- 用户可选择是否接收回复（勾选"需要回复"时，管理员可通过邮箱回复）

**预估时间**：2–3 周
**依赖**：阶段一、二、三的基础；可与阶段四部分并行

## 依赖关系

```
阶段一（后端解耦）
  ├── 阶段二（前端重构）      ← 依赖稳定的 API 结构
  ├── 阶段三（管理后台升级）  ← 依赖拆分后的路由模块
  │     └── 阶段四（数据统计） ← 依赖管理后台基础
  └── 阶段五（质量+社区）     ← 贯穿全流程，可部分并行
```

- 阶段二至阶段五是**逻辑依赖**，不是严格阻塞——前端拆分不阻止管理后台工作
- 阶段五的测试部分**应尽早开始**（拆分一个模块就可以写一个模块的测试），不要拖到最后
- 安全加固分散在开发进程中——CORS 和安全头在部署时做，rate limit 在拆分限流模块时做

## 成功标准

每个阶段结束时的验收条件：

1. **阶段一**：所有 API 端点仍正常工作 → 通过核心流程手动回归
2. **阶段二**：Lighthouse 性能评分提升（目标 80+），移动端完整可用
3. **阶段三**：完成一次完整的审核→驳回→通知→用户修改→重新提交→审核通过的闭环
4. **阶段四**：仪表盘数据与数据库直接查询结果一致，CSV 可在 Excel 打开
5. **阶段五**：`node --test` 全部通过，安全头/CORS 策略在部署后验证
